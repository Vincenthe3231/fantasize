CHAPTER 1 — Overview of Formal Methods

What Are Formal Methods?

Formal methods sit at the intersection of pure mathematics and software engineering. From a software engineering perspective, they refer to a collection of mathematical modelling techniques applicable to computer system design. Every part of a program is expressed in a formal language with well-defined semantics, making it possible to treat the program as a mathematical theory and to reason about its properties before it is ever executed. The central promise of formal methods is straightforward: they help you understand software before you run it.

Formally:

Formal Methods = Formal Specification + Formal Verification

Both of these components are grounded in set theory, logic, and algebra.

Features of Formal Methods

Formal methods are distinguished by several key characteristics. Strong typing provides a type system richer than those found in ordinary programming languages, offering economy of expression and built-in consistency checks. A built-in computational model enables simpler type-checking constraints and enhanced proof-checking. Modularisation allows a specification to be broken into independent modules, and parameterised modules further improve reusability. Total functions are assumed by most logics, and subtypes make them more flexible. Axioms and definitions must be used carefully to avoid inconsistencies; the definitional principle guarantees that definitions are well-formed.

Benefits of Formal Methods

Formal methods bring several measurable advantages to software development.

They increase confidence by providing a precise, unambiguous description of requirements, clarifying what the customer actually needs and eliminating inconsistencies. They support early defect detection by applying mathematical analysis to the earliest design artefacts, which reduces the cost of fixing errors because defects are caught long before coding begins. They contribute to the overall quality of the final product through complete verification across the entire state space of a system — meaning that any property proved to hold will hold for all possible inputs. This property is known as completeness. They facilitate correctness through rigorous mathematical techniques and model checkers that explore every execution path, including all thread interleavings in concurrent systems. Formal methods also support abstraction, providing a precise, high-level description of a complex system without drowning the reader in implementation details. In regulated industries such as aviation, they are considered trustworthy because they provide concrete, verifiable evidence. Finally, effective test cases can be derived systematically from a formal specification.

Limitations of Formal Methods

Despite their strengths, formal methods have real limitations. There is no guarantee of completeness: actual user requirements often differ from stated requirements and evolve over time, and no formal method can verify that a specification captures the complete intent of its users. There is also no guarantee of correctness: proving correctness of a program that was not written with proof in mind is practically impossible; correctness proofs are only feasible when programming and proof proceed simultaneously. Formal methods struggle with complex language features whose semantics are not formally defined or are too intricate to be practically useful. They require sound mathematical knowledge from developers, are difficult to communicate to non-technical stakeholders, carry a steep learning curve, and are often time consuming and expensive — the cost of specification alone can exceed a project's budget.

Formal Specification

A formal specification is a set of well-formed statements describing what a software system must do, not how it is to be implemented. It uses mathematics to describe system behaviour and desired properties at an abstract level.

Formal specification has two core activities:

Modelling uses mathematical models (such as Z) to describe and predict program behaviour accurately. Modelling makes program behaviour predictable, which is essential for safety-critical systems.

Design organises the internal structure of a program along two dimensions. Partition divides the whole system into independently developable modules. Refinement (also called reification) progressively adds detail, moving from an abstract model that satisfies the original requirements toward a concrete design closer to executable code.

Formal Specification Approaches

Formal specification comprises two fundamental approaches.

Model-based specification expresses the system as a state model built from well-understood mathematical entities such as sets and functions. System operations are described in terms of how they transform the system state. State changes are defined using pre-conditions (what must be true before an operation) and post-conditions (what is true after). The state of the system is never hidden. Z, VDM, and B are canonical sequential model-based languages; CSP and Petri Nets model concurrent systems.

Property-based specification describes a system indirectly by stating a set of properties using axioms and rules. It consists of signatures (the syntax of operations) and equations (axioms defining the semantics). The algebraic approach views a data type as an algebra; examples include OBJ and Larch. The axiomatic approach defines operation syntax and describes behaviour by providing a model; LOTOS is a key example.

Formal Verification

Formal verification is the act of proving or disproving that code satisfies its specification. Its two principal forms are theorem proving and model checking.

In theorem proving, a proof is a convincing demonstration constructed as a series of small, rule-justified steps — based only on the specification and program text, never on execution. Proofs eliminate the ambiguity and subjectivity of informal reasoning and can be done manually or with automated assistance. Because a proof considers all cases, it provides greater confidence than testing, which samples only some.

In model checking, a finite model of the system is built and an algorithm automatically checks whether a desired property holds in that model. Model checkers such as SMV, NuSMV, and Cadence explore all reachable paths in the computational tree derived from the state machine. Formal verification is most commonly applied to safety-critical systems (aircraft, nuclear stations) and embedded systems.

Formal Specification Languages

A formal specification language has a formally defined syntax (mechanically processable notation), semantics (objects defined unambiguously by mathematical means), a set of relations (rules for satisfying the specification), and operates at a level of abstraction above source code. These languages are generally non-executable — they specify what to compute, not how. Most are based on axiomatic set theory or higher-order logic. Notable examples include Z, VDM, B-Method, Alloy, JML, Petri Nets, LOTOS, and ASMs.

CHAPTER 2 — Z Specification Language

The Z Language

Z (pronounced "Zed") is the most widely used formal specification language. It is a model-based notation grounded in Zermelo-Fraenkel set theory and first-order predicate logic. Z describes the functionalities and desired results of a system without stating the "how". A system is modelled through its state (a collection of state variables and their values) and operations (functions that change that state). Z organises behaviour by describing possible states, initial states, state changes, and state queries.

The central graphical construct of Z is the schema, which provides an effective, modular structuring mechanism. Schemas are specification building blocks that improve readability, allow modularity, and can be understood with relative ease.

Z Fundamental Concepts: Sets

In Z, everything is a set. A set is any well-defined collection of distinct objects. There is no ambiguity about membership, and elements within a set are distinguishable from one another.

Defining sets. The symbol $==$ means "defined as":

$$\text{Oceans} == {\text{Atlantic}, \text{Arctic}, \text{Indian}, \text{Pacific}}$$

Membership. If $x$ is a set and $s$ is a member, write $s \in x$. If $s$ is not a member, write $s \notin x$.

Empty set. A set with no elements is denoted $\emptyset$.

Singleton set. A set containing exactly one element, such as ${a}$.

Subsets. $A \subseteq B$ if and only if every element of $A$ is also in $B$:

$$A \subseteq B \iff \forall x \bullet (x \in A \Rightarrow x \in B)$$

Proper subsets. $A \subset B$ means $A \subseteq B$ and $A \neq B$.

Power set $\mathbb{P}$. The power set of $A$, written $\mathbb{P}(A)$, is the set of all subsets of $A$. For $A = {x, y, z}$:

$$\mathbb{P}(A) = {\emptyset, {x}, {y}, {z}, {x,y}, {x,z}, {y,z}, {x,y,z}}$$

Finite set $\mathbb{F}$. A set with exactly $n$ distinct elements. The cardinality operator $#$ gives the number of elements: $#{1, 2, 4} = 3$.

Infinite sets. $\mathbb{N} = {0, 1, 2, 3, \ldots}$, $\mathbb{Z} = {\ldots, -2, -1, 0, 1, 2, \ldots}$, $\mathbb{Q}$, $\mathbb{R}$ are all infinite.

Set Operations

Given sets $A$ and $B$:

Union $A \cup B$: all elements in $A$, $B$, or both.

Intersection $A \cap B$: all elements in both $A$ and $B$.

Disjoint sets: $A \cap B = \emptyset$.

Set difference $A \setminus B$: elements in $A$ but not in $B$. For example, ${1,2,3,4,8,9} \setminus {1,2,3} = {4,8,9}$.

Set Comprehension

When full enumeration is impossible, set comprehension is used:

$${x : S \mid P(x)} \quad \text{"the set of all } x \text{ in } S \text{ satisfying } P(x) \text{"}$$

With a term function $f$:

$${x : S \mid P(x) \bullet f(x)}$$

Examples:

$${x : \mathbb{N} \mid x < 20 \bullet x^2} \quad \text{squares of naturals less than 20}$$

$${x : \mathbb{Z} \mid (\exists y : \mathbb{Z} \bullet x = 2y) \bullet x^2} \quad \text{squares of even integers}$$

$${x : \mathbb{Z} \mid (x \bmod 4 = 0) \land (x > 0) \bullet x * x} \quad \text{squares of positive multiples of 4}$$

Quantifiers

Universal quantification $\forall$ asserts a predicate holds for all members of a type:

$$\forall x : \mathbb{N} \bullet x + 1 > 0$$

Existential quantification $\exists$ asserts at least one member satisfies a predicate:

$$\exists x : \mathbb{N} \bullet x + 1 > 1$$

Unique existential quantification $\exists_1$ asserts exactly one member satisfies the predicate:

$$\exists_1 x : \mathbb{N} \mid x < 10 \bullet x + 9 > 12$$

Z Types

Z is strongly typed — every identifier must be declared. Z has three type categories.

Built-in types are $\mathbb{Z}$ (integers) and $\mathbb{N}$ (natural numbers): $$\mathbb{N} == {n : \mathbb{Z} \mid n \geq 0}, \qquad \mathbb{N}_1 == {n : \mathbb{Z} \mid n > 0}$$

Basic types (given sets) are introduced using square brackets: $$[NAME], \quad [STUDENTNAME, STUDENTID]$$

Basic types must use ALL capital letters; no underscores, digits, spaces, or other symbols are permitted. They represent sets whose internal structure is invisible — used to model global entities without specifying internal details.

Free types are enumerated using the data type definition symbol $::=$ and the branch separator $|$:

$$COLOUR ::= violet \mid indigo \mid blue \mid green \mid yellow \mid orange \mid red$$ $$POSITION ::= off \mid on$$

Z Identifiers

Z identifiers are composed of letters, digits, and underscores. Upper and lower case are distinct. The first character must be a lowercase letter; if more than one word is used, subsequent words begin with uppercase letters (camelCase). Identifiers cannot begin with a digit.

Decorations carry semantic meaning:

  • A trailing prime $'$ indicates the value of a variable after an operation (e.g., $student'$).
  • A trailing $?$ indicates an input variable (e.g., $name?$).
  • A trailing $!$ indicates an output variable (e.g., $result!$).

Axiomatic Definition

Axiomatic definitions declare global variables and optional constraints. They apply throughout the entire specification:

$$ \begin{array}{|l|} \hline maxStudent : \mathbb{N} \ \hline maxStudent = 100 \ \hline \end{array} $$

If there is no constraining predicate, the predicate part is omitted. Global constants may also be declared with the abbreviation definition symbol:

$$minimum == 0$$

Z Schema

A schema is a named, modular unit that structures a Z specification. It describes both static and dynamic aspects of a system.

Static aspects covered by a State Space Schema include the state variables the system can occupy and the invariant (constraint) relationships maintained as the system moves between states.

Dynamic aspects covered by Operation Schemas include the operations possible, the relationship between inputs and outputs, and state transitions described through pre-conditions and post-conditions.

A complete Z specification involves:

  1. A state space schema describing the main data components.
  2. An initialisation schema showing the initial values.
  3. Operation schemas describing normal operations.

Each schema has three parts:

  • Schema Name: always begins with a capital letter; multi-word names combine words with each word capitalised (e.g., AddCustomer). No underscores, digits, spaces, or symbols.
  • Declaration part: introduces variables and assigns them types. Each line is implicitly terminated with a semicolon.
  • Predicate part: places constraints on those variables. Multiple predicates are connected by conjunction ($\land$). Schema predicates are always TRUE.

Graphical (box) form:

$$ \begin{array}{|l|} \hline \textbf{SchemaName} \ \hline variable : Type \ \hline predicate \ \hline \end{array} $$

Text form:

$$SchemaName \cong [Declarations \mid Predicates]$$

Z Example: The Counter System

Step 1 — Axiomatic definition (global constant):

$$ \begin{array}{|l|} \hline maximum : \mathbb{N} \ \hline maximum = 100 \ \hline \end{array} $$

Step 2 — State space schema:

$$ \begin{array}{|l|} \hline \textbf{Counter} \ \hline total : \mathbb{N} \ \hline total \leq maximum \ \hline \end{array} $$

Step 3 — Initial state schema:

$$ \begin{array}{|l|} \hline \textbf{InitCounter} \ \hline Counter' \ \hline total' = 0 \ \hline \end{array} $$

CHAPTER 3 — Z Structure

Z Structure Overview

Z models complex systems through four structural mechanisms: Tuples (records), Relations (tables and linked data), Functions (lookup tables), and Sequences (lists and arrays). Bags are discussed separately in Chapter 5.

Tuples

A tuple is an ordered record. The Cartesian product of sets $S$ and $T$, written $S \times T$, is the set of all ordered pairs drawn first from $S$ and then from $T$:

$${1, 2, 3} \times {4, 5} = {(1,4), (1,5), (2,4), (2,5), (3,4), (3,5)}$$

To model a multi-field record, declare composite types:

$$[NAME] \qquad ID == \mathbb{N} \qquad DEPT ::= admin \mid manufacturing \mid research$$

$$EMPLOYEE == ID \times NAME \times DEPT$$

For multiple records, use the power set $\mathbb{P}$:

$$staff : \mathbb{P}, EMPLOYEE$$

Relations

A relation is a set of ordered pairs. It models many-to-many links between elements. In Z, a binary relation from $A$ to $B$ is written:

$$A \leftrightarrow B \quad \text{which stands for } \mathbb{P}(A \times B)$$

A pair may be written using maplet notation: $a \mapsto b$ is equivalent to the pair $(a, b)$.

The domain of a relation $R$ is the set of all first components: $\text{dom}, R$. The range is the set of all second components: $\text{ran}, R$.

Domain restriction $S \triangleleft R$ selects pairs whose first component is in $S$:

$${2} \triangleleft {1 \mapsto a, 2 \mapsto b, 3 \mapsto c} = {2 \mapsto b}$$

Range restriction $R \triangleright S$ selects pairs whose second component is in $S$:

$${1 \mapsto a, 2 \mapsto b, 3 \mapsto c} \triangleright {a, c} = {1 \mapsto a, 3 \mapsto c}$$

Domain anti-restriction $S \mathrel{\text{⩤}} R$ removes pairs whose first component is in $S$:

$${2} \mathrel{\text{⩤}} {1 \mapsto a, 2 \mapsto b, 3 \mapsto c} = {1 \mapsto a, 3 \mapsto c}$$

Range anti-restriction $R \mathrel{\text{⩥}} S$ removes pairs whose second component is in $S$:

$${1 \mapsto a, 2 \mapsto b, 3 \mapsto c} \mathrel{\text{⩥}} {b} = {1 \mapsto a, 3 \mapsto c}$$

Relational image $R(!(S)!)$ returns the set of range elements corresponding to domain elements in $S$:

$${1 \mapsto a, 2 \mapsto b, 3 \mapsto c}(!({1,3})!) = {a, c}$$

Inverse $R^{\sim}$ swaps domain and range by reversing each pair:

$${1 \mapsto a, 2 \mapsto b, 3 \mapsto c}^{\sim} = {a \mapsto 1, b \mapsto 2, c \mapsto 3}$$

Relational overriding $Q \oplus R$ updates $Q$ with pairs from $R$, replacing any pairs in $Q$ whose domain elements appear in $R$:

$$phone \oplus {Anne \mapsto 1108}$$

replaces Anne's old number with 1108, leaving all others unchanged.

Relational composition $Q \mathbin{;} R$ merges two relations by linking the range of $Q$ with the domain of $R$:

$$hasPhone \mathbin{;} phoneInRoom = {roy \mapsto A306, tom \mapsto A39, \ldots}$$

Functions

A function is a special relation in which each domain element appears at most once. There are no two distinct pairs with the same first component. Functions model many-to-one (or one-to-one) relationships.

Function application associates a domain element with its unique range element: $f, x$ or $f(x)$. Application is undefined if $x \notin \text{dom}, f$.

Partial Function ($\mathrel{\text{⇸}}$)

A partial function is defined for some values of its source:

$$f : X \mathrel{\text{⇸}} Y$$

For example, ${(1,3),(4,9),(8,3)}$ over $\mathbb{N} \times \mathbb{N}$ is partial because its domain ${1,4,8}$ is a proper subset of $\mathbb{N}$.

Total Function ($\rightarrow$)

A total function is defined for every element of its source:

$$f : X \rightarrow Y$$

Function application can always be safely used with a total function.

Properties of Functions

Injection (one-to-one): No two domain elements map to the same range element.

  • Partial injection: $A \mathrel{\text{⤔}} B$
  • Total injection: $A \rightarrowtail B$

Surjection (onto): The range equals the entire target.

  • Partial surjection: $A \mathrel{\text{⤀}} B$
  • Total surjection: $A \twoheadrightarrow B$

Bijection: Both injective and surjective; every element of the source maps to a distinct element of the target, covering all of it.

  • Bijection: $A \mathrel{\text{⤖}} B$

Function notations summary:

Symbol Meaning
$\rightarrow$ Total function
$\mathrel{\text{⇸}}$ Partial function
$\rightarrowtail$ Total injection
$\mathrel{\text{⤔}}$ Partial injection
$\twoheadrightarrow$ Total surjection
$\mathrel{\text{⤀}}$ Partial surjection
$\mathrel{\text{⤖}}$ Bijection

Function overriding uses $\oplus$:

$$phone \oplus {peter \mapsto 1555} = {peter \mapsto 1555, paul \mapsto 1488, mary \mapsto 1777}$$

Birthday Book Example

The Birthday Book illustrates a complete Z specification.

Basic types: $$[NAME, DATE]$$

State space schema:

$$ \begin{array}{|l|} \hline \textbf{BirthdayBook} \ \hline known : \mathbb{P}, NAME \ birthday : NAME \mathrel{\text{⇸}} DATE \ \hline known = \text{dom}, birthday \ \hline \end{array} $$

Initial state:

$$ \begin{array}{|l|} \hline \textbf{InitBirthdayBook} \ \hline BirthdayBook' \ \hline known' = \emptyset \ \hline \end{array} $$

AddBirthday operation (adds a new name and date):

$$ \begin{array}{|l|} \hline \textbf{AddBirthday} \ \hline \Delta BirthdayBook \ name? : NAME \ date? : DATE \ \hline name? \notin known \ birthday' = birthday \oplus {name? \mapsto date?} \ \hline \end{array} $$

The $\Delta$ convention indicates that the state changes. The $\Xi$ convention (no delta) indicates that the state remains unchanged.

Remind operation (queries who has a birthday today, no state change):

$$ \begin{array}{|l|} \hline \textbf{Remind} \ \hline \Xi BirthdayBook \ today? : DATE \ cards! : \mathbb{P}, NAME \ \hline cards! = {n : known \mid birthday(n) = today?} \ \hline \end{array} $$

CHAPTER 4 — Z Schema Operators and Error Scenarios

Schema Operators

Z provides a rich calculus for combining schemas, making it possible to construct complex specifications from smaller, reusable components.

Schema Conjunction ($\land$)

The conjunction of schemas $S$ and $T$, written $S \land T$, merges both declaration parts and conjoins both predicates. Variables shared between the two schemas must have matching types.

$$Division \cong Quotient \land Remainder$$

Schema Disjunction ($\lor$)

The disjunction $S \lor T$ merges both declaration parts but disjoins the predicates, allowing the specification to describe alternative behaviours:

$$T_Division \cong Division \lor DivideByZero$$

Schema Negation ($\lnot$)

The negation $\lnot S$ retains the same declaration as $S$ but negates the predicate part.

Schema Inclusion

Including a schema name in the declaration part of another schema merges their declarations and conjoins their predicates. It promotes reuse and modularity:

$$EnhancedBoxOffice \cong [BoxOffice; \ldots \mid \ldots]$$

Schema Hiding ($\setminus$)

Hiding existentially quantifies specified variables out of a schema. If $S$ has a variable $b$:

$$S \setminus (b) \equiv \exists b : T \bullet S$$

This is useful for concealing intermediate variables that are not part of the external interface.

Schema Composition ($\mathbin{;}$)

Schema composition describes the effect of one operation followed immediately by another. The after-state of the first operation is identified with the before-state of the second. The composition symbol is the fat semicolon $\mathbin{;}$.

The procedure involves:

  1. Replacing primed ($'$) variables in the first schema with double-primed ($''$) variables.
  2. Replacing unprimed variables in the second schema with double-primed variables.
  3. Existentially quantifying over the double-primed variables.

Schema Piping ($\gg$)

Schema piping $S \gg T$ connects the output variables of $S$ to the input variables of $T$ that share the same name and type. Those matched (piped) variables are hidden in the result. Unmatched inputs and outputs remain visible.

Schema Implication ($\Rightarrow$) and Equivalence ($\Leftrightarrow$)

$S \Rightarrow T$ states that whenever $S$ holds, $T$ must also hold. $S \Leftrightarrow T$ states that $S$ and $T$ are logically equivalent ($S \Rightarrow T$ and $T \Rightarrow S$).

Error Scenarios

A robust Z specification must account for situations where preconditions fail. The approach has three systematic steps.

Step 1 — Define a free type for all reports:

$$REPORT ::= success \mid classFull \mid alreadyEnrolled \mid notEnrolled \mid alreadyPassed \mid notPassed$$

Step 2 — Create a Success schema (used whenever a normal operation succeeds):

$$ \begin{array}{|l|} \hline \textbf{Success} \ \hline report! : REPORT \ \hline report! = success \ \hline \end{array} $$

Step 3 — Create error schemas for each identified failure condition. Error schemas never update any state variable.

The Class System: A Complete Example

Basic type and axiomatic definition:

$$[STUDENT]$$

$$ \begin{array}{|l|} \hline maxClassSize : \mathbb{N} \ \hline maxClassSize = 20 \ \hline \end{array} $$

State space schema:

$$ \begin{array}{|l|} \hline \textbf{Class} \ \hline enrolled : \mathbb{F}, STUDENT \ passed : \mathbb{F}, STUDENT \ \hline passed \subseteq enrolled \ #enrolled \leq maxClassSize \ \hline \end{array} $$

Initial state:

$$ \begin{array}{|l|} \hline \textbf{InitClass} \ \hline Class' \ \hline enrolled' = \emptyset \ passed' = \emptyset \ \hline \end{array} $$

EnrolOk operation (student joins the class):

$$ \begin{array}{|l|} \hline \textbf{EnrolOk} \ \hline \Delta Class \ student? : STUDENT \ \hline #enrolled < maxClassSize \ student? \notin enrolled \ enrolled' = enrolled \cup {student?} \ passed' = passed \ \hline \end{array} $$

Error schemas for enrolment:

$$ \begin{array}{|l|} \hline \textbf{ClassFull} \ \hline \Xi Class \ student? : STUDENT \ report! : REPORT \ \hline #enrolled \geq maxClassSize \ report! = classFull \ \hline \end{array} $$

$$ \begin{array}{|l|} \hline \textbf{AlreadyEnrolled} \ \hline \Xi Class \ student? : STUDENT \ report! : REPORT \ \hline student? \in enrolled \ report! = alreadyEnrolled \ \hline \end{array} $$

Complete schema for the enrolment operation:

$$Enrol \cong (EnrolOk \land Success) \lor ClassFull \lor AlreadyEnrolled$$

Similarly for the other operations:

$$Complete \cong (CompleteOk \land Success) \lor NotEnrolled \lor AlreadyPassed$$

$$LeaveWithCertificate \cong (LeaveWithCertificateOk \land Success) \lor NotPassed$$

The general pattern is: combine the normal operation with the Success schema using conjunction ($\land$), then combine this with all error schemas using disjunction ($\lor$).

CHAPTER 5 — Extended Z Structure: Sequences and Bags

Sequences

A sequence is an ordered collection of objects. Unlike sets, sequences allow repeated elements and maintain a defined ordering. Unlike tuples, sequences are not fixed in length. A sequence is actually a finite function whose domain is drawn from consecutive non-zero natural numbers (indices):

$$weekday = {1 \mapsto mon, 2 \mapsto tue, 3 \mapsto wed, 4 \mapsto thu, 5 \mapsto fri}$$

Sequences can model arrays, lists, queues, and other sequential structures. In Z, sequences are notated inside angle brackets $\langle$ and $\rangle$:

$$weekday = \langle mon, tue, wed, thu, fri \rangle$$

Types of Sequence

  • Empty sequence: $\langle \rangle$
  • Normal (possibly empty) sequence: $\text{seq}$
  • Non-empty sequence: $\text{seq}_1$
  • Injective sequence (no duplicate elements): $\text{iseq}$

Declaring a sequence variable:

$$ \begin{array}{|l|} \hline weekday : \text{seq}_1, DAY \ \hline \end{array} $$

Sequence Operations

Since a sequence is a function, function application applies: $weekday(1) = mon$ and $weekday(6)$ is undefined.

Operation Meaning
$\text{head}, s$ First element of $s$
$\text{last}, s$ Last element of $s$
$\text{tail}, s$ $s$ without its first element
$\text{front}, s$ $s$ without its last element
$s \frown t$ Concatenation of $s$ then $t$
$s \upharpoonright A$ Filter: elements of $s$ that appear in $A$, order preserved
$A \upharpoonleft s$ Extraction: elements at indices $A$ of $s$
$\text{squash}, f$ Compact a function with non-consecutive natural-number domain into a sequence
$#s$ Cardinality (length) of sequence $s$

Concatenation example:

$$\langle sun \rangle \frown weekday \frown \langle sat \rangle = \langle sun, mon, tue, wed, thu, fri, sat \rangle$$

Filter example:

$$weekday \upharpoonright \langle tue, wed \rangle = \langle tue, wed \rangle$$

Extraction example:

$${2, 4, 6} \upharpoonleft weekday = \langle tue, thu \rangle$$

Squash example:

$$\text{squash}, {4 \mapsto c, 2 \mapsto b, 6 \mapsto d} = \langle b, c, d \rangle$$

Bags

A bag (also called a multiset) is an unordered collection of objects that may contain duplicates. This distinguishes it from a set (which has no duplicates and no order) and from a sequence (which has order and may have duplicates).

A bag is formally a partial function from elements to positive natural numbers, recording the multiplicity of each element:

$$bag, X == X \mathrel{\text{⇸}} \mathbb{N}_1$$

Bags are enumerated using double angle brackets $\llbracket$ and $\rrbracket$:

$$num == \llbracket 1, 1, 2, 3 \rrbracket \quad \text{equivalent to } {1 \mapsto 2, 2 \mapsto 1, 3 \mapsto 1}$$

The order in which elements are written is irrelevant: $\llbracket a, a, b \rrbracket = \llbracket a, b, a \rrbracket$.

Bag Operations

Counting multiplicity. To find how many times $x$ occurs in bag $B$:

$$B # x \quad \text{or} \quad \text{count}, B, x$$

Example: if $rainMonth == \llbracket jan, jan, feb, dec \rrbracket$ then $rainMonth # jan = 2$ and $rainMonth # apr = 0$.

Bag scaling $n \otimes B$: multiplies the multiplicity of every element in $B$ by $n$:

$$2 \otimes \llbracket jan, jan, feb \rrbracket = \llbracket jan, jan, jan, jan, feb, feb \rrbracket$$

Theorems about scaling: $n \otimes \llbracket \rrbracket = \llbracket \rrbracket$; $0 \otimes B = \llbracket \rrbracket$; $1 \otimes B = B$.

Bag membership $x \sqsubseteq B$ (or $x, \mathbf{in}, B$): true if and only if $x$ appears in $B$ at least once.

Sub-bag $B_1 \sqsubseteq B_2$: true if each element of $B_1$ occurs in $B_2$ no more often than in $B_1$.

Bag union $B_1 \uplus B_2$: combines two bags, summing multiplicities.

$$\llbracket jan, jan, feb \rrbracket \uplus \llbracket jan \rrbracket = \llbracket jan, jan, jan, feb \rrbracket$$

Bag difference $B_1 \setminus B_2$: subtracts multiplicities of $B_2$ from $B_1$.

$$\llbracket jan, jan, feb \rrbracket \setminus \llbracket jan \rrbracket = \llbracket jan, feb \rrbracket$$

Making a bag from a sequence using $\text{items}$:

$$\text{items}, \langle a, b, a, b, c \rangle = \llbracket a, a, b, b, c \rrbracket$$
